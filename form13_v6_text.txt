This API is tested on the production ODeX system, with demo users and only three demo shipping lines. DEMO is the general line. DEBET follows the MSC configuration. DEALP follows the Hapag-Lloyd configuration. Do not send any other shipping line code while testing. A request with a live line code is a real Form 13 on production. Live line codes are shared only after UAT sign-off. Payor code, secret key and screen login are shared after the walkthrough.
1. What this guide covers
Form 13 is the export gate-pass a payor files with a shipping line so a container can enter an Indian port. This guide is the contract for that filing by API. It lists every field, when the field is mandatory, which code to send, and what the response means.
Form type in every Form 13 call is F13. The same URL also accepts Form 11 and cart-in. Those forms are not described here. Sending the wrong form type applies the wrong rules.

2. Form 13 flow
ODeX shares the payor code (pyrCode) and the secret key. The same payor must be set up for Form 13 integration.
Download the full vessel list (section 5). Repeat every day, and again whenever a line opens a vessel, using the last update time you stored.
Download the POD list the same way (section 6). A POD that is not on that list for the terminal and service is rejected.
On the Form 13 screen, confirm the shipping line, shipper, issue-to, terminal login and haulier. If a value appears twice, use the one on the screen. During testing the line code is only DEMO, DEBET or DEALP.
Build one JSON for one booking. Put every container of that booking in cntrList. Put every shipping bill of a container in that container's sbDtlsVo.
Set status to Requested on each container that should go to the line now. Leave it off, or send NOT_SUBMITTED, to save a draft.
Attach the PDFs whose titles the port, cargo and origin require. Convert each file to Base64.
Build hashKey with the rule in section 4 and POST saveF13.
If schema_validation is FAIL, correct the format and send the request again as a new request (no odexRefNo).
If business_validation is FAIL, correct the business error and send again as a new request.
On SUCCESS, store odexRefNo and each container status. This number is the key for every later call.
To correct a request that is still Not Submitted or Requested on every container, send the full JSON again with the same odexRefNo.
Poll the status API until the line verifies or confirms the container. The PIN, when the line issues one, is on that response.
To withdraw a verified or confirmed container, call the cancellation API. A rejected, awaiting-VGM or already confirmed container cannot be corrected with odexRefNo; follow the message on the response.
One odexRefNo belongs to one booking, one vessel, one port and one line. Do not mix bookings in one call. Do not change the port on a re-request.

4. Hash key
hashKey is required when ODeX has marked the payor integration as checksum-required. It is the decimal CRC32 of a string with no separators. Use the raw JSON values, including an empty string when a value is blank. Do not add spaces.
API
String before CRC32
Vessel master and POD master
pyrCode + fromTs + secretKey
saveF13
bookNo + for each container, in array order: cntnrNo + vgmWt + vgmViaODeX + shipBillInvNo + secretKey
Status response (returned by ODeX)
bookNo + for each container: cntnrNo + vgm weight + verify flag + shipping bill number + secretKey
shipBillInvNo in the saveF13 hash is the container-level field. Shipping bills that exist only inside sbDtlsVo do not go into the hash unless you also send shipBillInvNo on the container. Send vgmWt and vgmViaODeX on every container, using an empty string when you have no weight, so the hash stays stable.
Worked example. bookNo BKDEMO001, one container MSCU1234563, vgmWt 18.50, vgmViaODeX N, shipBillInvNo blank, secretKey SECRET. The string is:
BKDEMO001MSCU123456318.50NSECRET
CRC32 decimal (this is the hashKey): 1345125986
A wrong hash on saveF13 returns “Kindly enter valid hashkey” or “Hash key is Invalid”, before the Form 13 is saved.
5. Vessel master
The vessel call returns the lines, vessels, VIA numbers, terminals, services and the CHA filing window. A Form 13 is accepted only when vessel name and VIA match a row for that line and port, the terminal matches that row, the service matches that row, and the call is inside the CHA window (chaValidFrm to chaValidTo). Outside that window the response is Error (1005): the vessel has been cut off.
Take the whole list in one call, then keep it current. Do not type vessel names from a spreadsheet that is a week old.
First call: fromTs = 2000-01-01 00:00:00. The response is every vessel created or updated since then. Store the greatest lastUpdatedOn.
Every day, and whenever a user asks to refresh: fromTs = that stored lastUpdatedOn. Merge the rows into the local table. Replace a row when line, port, vessel and VIA match.
A full reload is the same first call. Use it if the local table is suspected to be incomplete.
fromTs must be YYYY-MM-DD HH:MM:SS. A date without the time is rejected.
listTyp Gatepass (or omit it) returns Form 13 vessels. Do not send HBL for this guide.
bnfCode on each row is the shipping line code to send later in saveF13. It is the code of the line shown for Form 13. If a line is duplicated in master, this is the code to keep.

8. Shipping lines
bnfCode is the shipping line code of the line on the Form 13 screen. The vessel master returns that same code on every vessel of the line.
If master data contains the same line twice, use the row that is on the Form 13 dropdown: active, and enabled for Form 13. Do not send an inactive duplicate, and do not send a code that is not on that dropdown.

9. Several containers, several shipping bills
cntrList is the whole booking. Two containers means two objects. Each object has its own seals, weight, vehicle, haulier, status and sbDtlsVo. sbDtlsVo is the whole set of shipping bills for that container. Two bills means two objects in that array. Bills are not repeated at the header.
All containers share the header: line, vessel, VIA, terminal, service, POD, booking, shipper, origin and cargo type.
A duplicate container number inside the request is rejected.
Requested on a container submits that container. You can submit every container in the same call.
If any container is Requested, the submit checks (seals, VGM, hazardous, ODC, vehicle, attachments) run for the request.
The success response has one odexRefNo and one entry per container.

11. Correction by odexRefNo
A correction is the same API, saveF13, with the odexRefNo from the first success, and the full corrected JSON. ODeX updates that request. It does not create a second number.
Allowed only when every container on that request is NOT_SUBMITTED or REQUESTED.
If any container is verified, confirmed, rejected, awaiting VGM, cancelled, or in a cancellation request, the response is: Re-request can only be done for requested and not submitted requests.
locId must be the same port as the original. A different port is rejected.
An unknown odexRefNo returns invalid odexRefNo.
An existing container is matched by cntnrReqId if you send it, otherwise by container number. A new container number is added. Send the containers that should remain.
Send the same attachments that are still required. A correction is checked with the same rules as a new request.
Open: correction using odexRefNo
12. Shipper name and code
shipperNm is always required, maximum 100 characters.
On a terminal that is integrated to the terminal shipper master (a terminal API is configured and the line has a liner code at that terminal — this is the Adani-family pattern), both the name and the code must match one active shipper for that port and terminal. ODeX then stores the name and the code from that master. Those are the values on the Form 13 shipper dropdown. A name that only looks similar is Error (1024).
On any other terminal, shipperNm is the name you send. shipperCd is not checked against that master.
If the same shipper is listed twice, send the name and the code shown on the screen for that port and terminal.
shipperCity is mandatory for Form 13 at Tuticorin, terminal DBGT.
13. Haulier
haulier is the transporter code on the container, not the transporter name. The list is the active haulier codes for that terminal and port. Adani terminals are refreshed from the terminal transporter feed, so the code on the screen is the code to send.
It is required for Form 13 when you submit (status Requested), the origin is not dock stuffed (C), and that terminal has at least one haulier. A code that is not on the list is Error (1053). If the same transporter is listed twice, send the code shown on the screen.
14. Issue to
issueTo is required for Form 13 on every terminal except NSIGT, NSICT, MICT, IGT and CCTL. For those five, leave it blank.
The value is the code in the Issue To dropdown for that line, port and terminal. The descriptions on the screen are Shipper and CHA. Send the code the screen submits, not a sentence. A value that is not on that list is Error (1017). If a code is duplicated, use the one on the screen.
15. Terminal login id
terminalLoginId is the id the terminal uses for the CHA. It is required when any of these is true:
The port is an exception port and the Form 13 screen shows Terminal Login Id as mandatory. That set includes Chennai, Kattupalli, Ennore, Paradip and Kolkata.
The terminal master says the login id is mandatory.
The terminal is a Mundra Adani terminal: ADANI, AMCT, AICTPL, ACMTPL or AMCT2.
On an Adani-integrated terminal the id must be a CHA code in the terminal cross-reference for that terminal and port. The workbook sheet “AMCT terminal login master” is that list for AMCT: send the code column, status ACTIVE. Other terminals use the same layout. If the screen shows a different code for the same company, send the screen code.
If you have no id, the Form 13 screen says to enter ALL_CHA / MUNCUST. At Hazira the screen says to enter OTH. For a DPE shipment, origin is W (on wheel) and the terminal login id is the CHA code, not OTHR.
